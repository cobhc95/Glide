key / pointer input on a headless `MainWindow` / `SettingsWindow` over temp folders of real image files.

`tests/Glide.Core.Tests/Release517SettingsUiTests.cs`, `tests/Glide.Core.Tests/Release517AssetTests.cs`); the rest already existed.

user's single-instance pipe or drives the desktop.

## Impossible headlessly (manual checks)

- Real Windows shell icon rendering: that Explorer / the taskbar / Open With show the new document icons (the "JPG" page with the Glide mark), the
  fuller app icon next to other apps, and that file-type icons refresh after `SHChangeNotify`. Tests cover the files, sizes and registry value naming only;
  actual registration writes (`RegisterInHive`) need a real registry hive and were deliberately not run.
- Real elevation / UAC: an actual elevated process (token elevation, session isolation, the elevated pipe peer) cannot be started from a test; the
  decision policy and a real same-user pipe are tested.
- Real tray icon (Speed Boost): showing / hiding the notification area icon, its menu, and a second Glide process leaving no icon behind.
  The decision policy, owner election and settings propagation are tested.
- Real OS drag and drop between applications and across real drives (cursor feedback, Windows shell data objects, a drop from another app).
  The headless drag events, the move / copy rule and its drive-letter / UNC cases are tested; a cross-drive drop was not performed.
- Real fullscreen / multi-monitor, DPI and taskbar behaviour that the overlay-mode chrome depends on (item 19) and the real overlay window.
- A real launch of Glide by another program (Explorer double-click, "Open with") reaching a running installed Glide.

## Observations

- Bug found and fixed: a tag click that arrived while an earlier tag change was still renaming (or the viewer was reloading the renamed
  picture) was dropped silently (`_tagChangeBusy`), and the ticks snapped back. `MainWindow.Tags.cs` now queues such clicks and applies them
  in order to the files as they are named by then, and shows the predicted ticks while they wait (so the next click toggles the pending state).
  A failed change drops the clicks queued behind it. Tests (written first, failing before the fix): E2E
  `Rapid_tag_clicks_in_the_viewer_are_all_applied_in_order_and_the_ticks_show_the_pending_state`,
  `Rapid_tag_clicks_in_the_Explorer_are_all_applied_to_every_selected_file`.
- No other product bug was found.

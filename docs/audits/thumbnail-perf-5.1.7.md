# Explorer thumbnails and image loading, 5.1.7: before / after

Scope: the Explorer tab's thumbnail decode (`ThumbnailDecode.DecodeToWidth`), a persistent thumbnail disk cache, reduced-size
decodes beyond JPEG, and the viewer's first paint. Everything below was measured headless (no Glide window is ever opened) by
`tools/perf/run-thumb-bench.ps1`, on fixtures generated by `tools/perf/generate_thumb_fixtures.py` (synthetic photo-like images,
deterministic, written to a temp folder, never to a photo library).

## Summary

| Area | Result |
|---|---|
| Thumbnail disk cache (new, on by default) | A cached thumbnail is one small file read: **0.11 - 0.35 ms for every format**, against 1 - 134 ms to decode it (camera JPEG with an MPF preview 9x, ordinary JPEG 38 - 140x, progressive JPEG 230 - 610x, WebP 190 - 260x, PNG 400 - 930x). Keyed by path + size + modified time + requested width, so a changed picture is decoded again. |
| TIFF thumbnails | **New.** Skia cannot read TIFF, so the Explorer tab showed the file-type glyph for every `.tif`. Now 24 MP LZW 29 - 39 ms, 24 MP uncompressed 8 - 11 ms, 4K 5 - 15 ms (parallel row bands, box reduction; the spread is run-to-run variation of a multi-threaded decode, see below). |
| BMP thumbnails | **7.4x** faster at 24 MP (51 -> 6.9 ms), 3.8x at 4K (16.6 -> 4.4 ms); first thumbnail in a process 3.1x / 1.7x. |
| WebP thumbnails | libwebp decodes straight to the tile size (no 96 MB intermediate frame): 1.1 - 1.3x warm (24 MP 71.8 -> 60 ms, 4K 26.6 -> 20 ms) and 1.2 - 1.4x for the first thumbnail in a process. Modest: libwebp's lossy decode is the cost, not the scaling. |
| WebP in the viewer | First view of a 24 MP lossy WebP without transparency: cold 139 -> 91 - 95 ms in every run (1.5x), warm 89 -> 65 ms in the final run (an earlier run of the same binaries measured 88 ms: libwebp's two-thread decode is sensitive to thread placement). 4K: cold 87 -> 63 ms, warm unchanged. WebP with transparency and the full-resolution decode stay with Skia (libwebp's full decode measured 177 ms against Skia's 97 ms for 24 MP). |
| Progressive JPEG thumbnails (second pass) | **5.9x**: 24 MP 96.5 -> 16.4 ms, 12 MP 47.0 -> 8.5 ms warm; first thumbnail in a process 105.7 -> 27.0 ms (3.9x). Only the first (DC) scan is decoded, through libjpeg's buffered-image mode at 1/8 scale (the TurboJPEG API cannot stop early). The 15 ms target for 24 MP was missed by 1.4 ms: about 7 - 10 ms of the 16 ms is libjpeg allocating and zero-filling the 72 MB whole-image coefficient array a progressive decode needs before it reads the first scan. |
| Baseline JPEG thumbnails (second pass) | Unchanged at 25 ms (24 MP) / 13 ms (12 MP). The thumbnail path already sets fast IDCT and plain upsampling and decodes straight to BGRA; measured with the TurboJPEG API alone, a 1/8 decode of the 24 MP file takes 22.6 ms with or without those flags (Huffman decoding every block is the floor), so about 2.5 ms of the 25 ms is everything else (header, area-average). |
| PNG thumbnails (second pass) | Unchanged (24 MP 132 ms, 4K 50 ms). zlib-ng (the inflate inside .NET) needs 89.8 ms for the 24 MP file's IDAT stream alone (36.6 ms for 4K, 62.9 ms for the alpha file), so inflate is 68 % of the time and cannot be skipped, and row filters (Up / Average / Paeth) depend on the previous row, so only the colour conversion and scaling of skipped rows could be saved: at most 1.2x for much more code, with sampled rows lowering quality. Not implemented. |
| Whole-folder time, 200 mixed pictures (second pass) | 16-thread PC, 152 px tiles, all thumbnails decoded: **989 ms (8 lanes, start of the work) -> 869 ms (new decoders, 8 lanes) -> 749 ms (12 lanes, the new default on a high-end PC)**; the cache turns a second visit into **5 ms**. See "Whole folder". |
| GIF, ICO thumbnails | Unchanged (16 ms / 1 ms); only the cache helps. |
| Viewer first paint, every other format | Unchanged (JPEG, PNG, GIF, ICO, BMP). The viewer already decodes TIFF / BMP / PNG at full size on purpose (`PrefersFullFirstFrame`) and JPEG through WIC / libjpeg-turbo at a reduced size. TIFF / BMP show 1.1 - 1.2x in the final run only: their full-decode path is untouched (an earlier run of the same binaries: 1.0x), so that is run-to-run variation. |

Hardware: AMD Ryzen 7 9700X (8 cores / 16 threads), 61.6 GB RAM, SATA SSD, Windows 11. Medians; 7 warm runs per cell, 5 fresh
processes per cold cell. Machine load was sampled between phases (see the end of this file); another agent was driving the UI
at the same time, so the runs were kept light (one benchmark process at a time) and every phase is flagged below if it was busy.

## What did not get faster, and why

- **PNG (50 - 134 ms at 24 MP)**: tried, no route found. A non-interlaced PNG is one deflate stream, so every pixel must be inflated whatever the
  output size, and the inflate alone is most of the time (`Glide.PerfBench png-probe`, zlib-ng through `ZLibStream`: 24 MP 89.8 ms of
  132 ms, 4K 36.6 of 50, alpha 62.9 of 78). Skipping rows saves only the conversion and scaling of the skipped rows, because the
  Up / Average / Paeth filters need the previous row; no libspng or libdeflate is vendored, and WIC's PNG decoder measured slower
  (160 ms for 24 MP). The disk cache covers repeat visits (0.14 ms).
- **Baseline JPEG (13 - 25 ms)**: at the floor of the TurboJPEG API (see the summary): Huffman decoding of every block is the cost at 1/8 scale.
- **GIF, ICO**: 16 ms / 1 ms already; no benefit from a native route.
- **Camera RAW**: not measured. No RAW writer exists to generate a fixture and the in-app Explorer thumbnails do not decode RAW
  (the Windows shell provider does, through the embedded preview).
- **HEIC / AVIF**: not available in the in-app Explorer thumbnails (no Skia or WIC codec on this PC; the viewer decodes them
  through the bundled codec providers, which the headless benchmark does not load). The native thumbnail route would use a WIC HEIC
  thumbnail if a PC had the codec, but the tile list does not offer these extensions, to avoid a failed decode per tile.
- **Run-to-run spread of the threaded decodes**: libwebp's decode runs the loop filter on a second thread (single-threaded it is
  1.7x slower: 113 vs 65 ms for the viewer's first view, 90 vs 55 - 69 ms for a thumbnail) and the TIFF / BMP decode uses up to 8
  row-band threads, so their speed depends on how the OS places the threads. Five complete suite runs of the same decoders
  measured WebP 24 MP thumbnails at 68 / 69 / 68 / 60 / 55 ms and TIFF 24 MP LZW at 38.5 / 38.5 / 38.6 / 29.0 / 29.1 ms; the
  unchanged formats stayed within 3 % of the baseline in the clean runs, so the machine itself was steady. The tables are the
  last run, which had three load samples above 35 % at phase boundaries (43 % after the thumbnail phase, 40 % and 51 % around the
  first-paint decode phase, from the other agent's work): its unchanged first-paint rows read up to 7 % slow (progressive 24 MP
  cold 129 -> 139 ms, warm 106 -> 109 ms) and should be read with that margin; the thumbnail rows were not affected (warm
  numbers match the previous run to 3 %).
- **HEIC / AVIF rows in the first-paint table**: "n/a" before only because the codec providers (`codecs\glidecodecs.dll`) were not next to
  the benchmark build then; they were present for the after run. It is not a speed difference.

## Whole folder: 200 mixed pictures

`Glide.PerfBench grid --dir <folder> --width 152 --lanes ...` decodes every file of a folder with N worker lanes pulling from one list
(what the Explorer tab's thumbnail gate does) and reports the time until all thumbnails exist, median of 3 passes after one untimed pass.
The folder (`tools/perf/make_grid_folder.py`, 1.6 GB of copies of the fixtures under distinct names): 70 JPEG (30 baseline 12 MP,
15 baseline 24 MP, 10 progressive 24 MP, 15 camera JPEG with an MPF preview), 35 PNG, 30 WebP (10 of them 24 MP), 25 TIFF, 15 BMP, 15 GIF, 10 ICO.
It measures the decode only (no UI thread, layout or bitmap upload), so the time to everything *visible* in the app is this plus the
UI's own work.

| Decode lanes | Before: start of the work (25 TIFFs had no thumbnail) | After: all 200 thumbnails |
|---:|---:|---:|
| 1 | 5816.8 ms | 4483.1 ms |
| 2 | 3027.6 ms | 2352.9 ms |
| 4 | 1633.7 ms | 1309.6 ms |
| 6 | 1190.1 ms | 1006.6 ms |
| **8 (the old default)** | **989.2 ms** | **868.6 ms** |
| **12 (the new default on a high-end PC)** | 818.1 ms | **748.5 ms** |
| 16 | 741.2 ms | 714.4 ms |
| 24 | - | 708.0 ms |
| 8, second visit, every thumbnail from the disk cache | - | **5.2 ms** (1 lane 24 ms) |

Lane tuning: 4 -> 8 lanes saves 440 ms, 8 -> 12 saves 120 ms, 12 -> 16 only 35 ms and 16 -> 24 nothing, so a high-end PC (12+ threads and 20+ GB)
now runs three quarters of its threads, up to 12 (`ImagePerformanceGovernor.ThumbnailDecodeLanes`), leaving four for the UI and the
other tabs; every other PC keeps half its threads, 2 - 8. The cap stays lower elsewhere because each lane can hold a decoded
frame (a 24 MP PNG is 96 MB). The second "before" column is not a like-for-like total: it skipped the 25 TIFFs (Skia fails on them
immediately), so the real gain of the new decoders is larger than the 12 % shown at 8 lanes.

## What changed in the code

- Second pass: `GlideJpeg.cpp` + `GlideJpegLib.h` (DC-only progressive decode; hand-written libjpeg declarations checked by the library's own structure size / version test), `ImagePerformanceGovernor.ThumbnailLanesFor`, `PerfBench grid | png-probe`.
- `Glide.Imaging/ThumbnailDiskCache.cs`: the persistent cache. One file per (path, width) under
  `%LOCALAPPDATA%\Glide\thumbnails\<2 hex>\`; header (magic, size, requested width, source length, source last-write ticks, path
  hash) + BGRA premultiplied pixels (24-bit BGR when opaque). Atomic writes (temp file + move), readers share read/delete, any
  failure is a miss, writes run on the thread pool. Size limit with least-recently-used trimming to 90 % (hits refresh the file's
  timestamp at most every 30 minutes); stale versions of the same picture and width are removed when the new one is stored.
- `Glide.App/Services/ThumbnailDecode.cs`: cache first, then libjpeg-turbo (JPEG), the native thumbnail bridge (WebP, TIFF, BMP, JPEG XR),
  then Skia. `ThumbnailCacheSettings.cs` connects it to Settings (`SettingsService.Publish` applies it on every publish).
- Native (`Glide.Native`): `GlideDecodeThumbnailW` (embedded thumbnail that covers the tile, banded parallel TIFF / BMP decode with an
  integer box reduction per band and an exact area-averaged fit, decoder-native size, Fant scaler), `GlideWebp.cpp` on the vendored
  libwebp 1.5.0 (decode only, threads on, `use_scaling`; thumbnails over a 4x reduction also skip the loop filter and fancy chroma
  upsampling), bounded WebP first view. Failures never cross the C boundary (`try/catch` in the export and in every band thread).
- Settings (Window & navigation): `explorer.thumbnailCache` (on by default), `explorer.thumbnailCacheMaxMb` (32 - 8192, default 512),
  `explorer.clearThumbnailCache` (button, shows the space used). "Clear image and thumbnail caches" in Reset also removes the folder.
- Explorer tab: `.webp`, `.jxr`, `.wdp`, `.hdp` now get thumbnails (TIFF was already listed but never decoded).

## Tests

39 new test cases (Glide.Core.Tests, all passing; full runs after the final change: Core 3015, Explorer 296, Input 21, 0 failures; `tools\quick-check.ps1` and the three audits pass):

- `ThumbnailDiskCacheTests` (12, plain instance tests): opaque and transparent round trip (24-bit storage), row-stride padding, misses for another width / picture / missing source, an edited picture is a miss and its old file is removed, least-recently-used trimming (oldest five of ten go), a read refreshes the LRU clock, background trim to 90 % of the limit, 8 threads reading and writing the same thumbnails never see a partial file and leave no `.tmp`, truncated / foreign / inconsistent files are misses and are deleted, Clear removes only cache files, over-size and empty requests are ignored, limit clamping.
- `ThumbnailDiskCacheDecodeTests` (7): the second `ThumbnailDecode.DecodeToWidth` is answered without decoding, a changed picture is decoded again, another width is another entry, cache off decodes every time and writes nothing, Settings start / resize / stop the shared cache, `SettingsService.Publish` applies the switch and limit and keeps an isolated profile's cache in its own folder, catalogue defaults and the Caches reset target.
- `ThumbnailScaledDecodeTests` (13): TIFF (banded 2.4 MP and 3000 x 800, generic 640 x 480) and BMP thumbnails are the right size and match the gradient to within 6 levels, the banded reduction agrees with the WIC scaler (mean difference under 3), a thumbnail is never larger than the picture, `ThumbnailDecode` returns TIFF / BMP thumbnails, libwebp thumbnail, viewer first view and bit-exact full frame of a lossless WebP, alpha kept in a WebP thumbnail, a damaged or empty WebP is declined, the tile list offers the new extensions.
- `ProgressiveJpegThumbnailTests` (7, second pass): the DC scan alone is the 1/8 picture (560 x 840 from 4480 x 6720, within 6 levels of Skia's 1/8 decode: this is also what validates the hand-written libjpeg structure layout), thumbnails at 236 / 152 / 104 px from it match Skia's within 8 levels per 16 x 24 cell, a baseline JPEG and a source too small for 1/8 keep the one-shot decode, a progressive file cut inside its DC scan and a garbage SOF are declined, the thumbnail lane rule (high-end 3/4 of the threads up to 12, others half up to 8).
- `ResetPlannerTests` gained one assertion for the cache folder (it is not Windows' `thumbcache_*.db`).

reflection, so one source measures both builds). `Glide.PerfBench thumb|thumb-one|webp-stress` are the new modes.
